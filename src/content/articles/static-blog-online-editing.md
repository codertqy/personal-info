把网站发布出去后，我很快发现了一个新问题：页面可以正常阅读，却找不到新增、编辑和删除文章的入口。最开始我以为是少做了一个按钮，后来才明白，这是静态博客的内容存储方式决定的。

## 文章其实是仓库里的文件

这个网站的每篇文章都保存在 `src/content/articles` 目录中，本质上是 Markdown 文件。Astro 在部署时读取这些文件，生成最终网页。访客打开的是已经构建好的结果，网页本身不会直接修改 GitHub 仓库里的源文件。

所以，给页面加一个“编辑”按钮并不能真正完成内容管理。要在线保存文章，还需要解决三个问题：

1. 确认操作者有仓库权限；
2. 把编辑结果写回 GitHub；
3. 让 Vercel 在文件变化后重新构建网站。

## 为什么没有直接增加数据库后台

传统方案可以开发登录系统、管理接口和数据库，但这会让一个简单的个人博客多出服务器、安全维护、数据备份等工作。我的需求只是管理 Markdown 文章，没有必要一开始就把架构做重。

最终我选择了 Pages CMS。它是一个面向 GitHub 静态网站的内容编辑器，不另外保存一份文章数据库，而是直接编辑仓库里的文件。

## 新的发布流程

仓库根目录加入 `.pages.yml` 后，编辑器就能识别文章标题、分类、标签、封面、草稿状态和正文。之后的流程变成：

```text
Pages CMS 中编辑并保存
          ↓
GitHub 仓库产生一次提交
          ↓
Vercel 检测变化并自动发布
```

这样既保留了 Markdown 文件容易迁移、可以查看历史的优点，也不用每次都在本地打开代码编辑器。日常短记录也使用相同方式管理。

## 仍然需要注意什么

内容后台不应该允许任何访客修改网站。Pages CMS 通过 GitHub 登录和仓库权限进行控制，所以第一次使用时需要安装它的 GitHub App，并只授权需要管理的仓库。

静态博客“只能看”并不是缺陷，而是它默认把内容发布和内容编辑分开了。现在补上的 CMS 是编辑层，GitHub 继续保存内容，Vercel 继续负责发布，各自只做一件事。
